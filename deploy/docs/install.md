# Installing Verity

**Task 42.** One stateless application, one PostgreSQL, optionally one
S3-compatible object store. Nothing else.

## Requirements

*   Docker Engine 24+ with the Compose plugin.
*   4 GB RAM, 20 GB disk for a small deployment.
*   An identity provider: either a Supabase project or any OIDC-compliant IdP
    (Keycloak, Entra ID, Okta, Auth0, Ping).

## Install

```bash
git clone <repository> verity && cd verity

# Generates deploy/config/verity.env with strong secrets (mode 0600),
# runs preflight, builds, migrates, bootstraps, starts, verifies.
./deploy/scripts/install.sh

# With the bundled object store:
VERITY_WITH_MINIO=1 ./deploy/scripts/install.sh
```

Then edit `deploy/config/verity.env` to point at your identity provider and
re-run. The installer never overwrites an existing env file.

**Back up `deploy/config/verity.env` separately.** It is not recoverable from
the deployment.

## Identity

### Supabase

```ini
VERITY_AUTH_PROVIDER=supabase
NEXT_PUBLIC_SUPABASE_URL=https://<project>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon key>
SUPABASE_JWT_SECRET=<jwt secret>
```

The anon key is inlined into the browser bundle by design and is protected by
RLS, not by secrecy. Changing it requires a rebuild.

### OIDC

```ini
VERITY_AUTH_PROVIDER=oidc
VERITY_OIDC_ISSUER=https://idp.example.com/realms/acme
VERITY_OIDC_CLIENT_ID=verity-web
VERITY_SESSION_SECRET=<generated by install.sh>
```

No Supabase variables are needed. The JWKS endpoint is discovered from the
issuer, and the discovery document's own issuer is checked before its keys are
trusted.

Verity **never creates a user from a token**. A person must already exist as an
identity in a tenant; an unknown principal resolves to no memberships and no
access. This is deliberate — the alternative lets anyone in the corporate
directory materialise identity inside a tenant.

## Storage

```ini
VERITY_STORAGE_DRIVER=s3
VERITY_S3_BUCKET=verity-media
VERITY_S3_ENDPOINT=http://objects:9000     # blank for AWS
VERITY_S3_ACCESS_KEY_ID=...
VERITY_S3_SECRET_ACCESS_KEY=...
VERITY_S3_FORCE_PATH_STYLE=true            # self-hosted servers
```

The same variables reach AWS S3, MinIO, Ceph RGW, Wasabi, Backblaze B2 or a
SeaweedFS S3 gateway. A deployment with no storage configured is valid: file
operations refuse at the point of use rather than at boot.

## TLS

The application speaks HTTP on `127.0.0.1:3000`. Put nginx, Caddy or Traefik in
front of it. TLS is not terminated inside the application — that would put
certificate rotation on the deployment's critical path for no security gain.

## Verify

```bash
./deploy/scripts/health.sh
```

Liveness and readiness are reported separately, because a process that is alive
with a dead database must not look the same as one that is down.
