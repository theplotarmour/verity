# ADR-016 — The scheduler may enumerate tenants

**Date:** 2026-08-28
**Status:** ACCEPTED
**Supersedes:** nothing. Extends ADR-013 and ADR-015.

## Context

ADR-015 bound scheduled work to an authenticated route, `POST /api/scheduled`, and
that route takes **one tenant per call**. Its own comment records why, and records
what would change the answer:

> Enumerating tenants here would be a cross-tenant read, and ADR-013 lists exactly
> three of those — adding a fourth is a deliberate act with its own decision, not
> something a cron endpoint does on the way past. One schedule entry per client is
> honest at Kent's scale; when there are enough clients for that to hurt, that is
> the requirement that forces the enumeration decision, and it can be answered then
> with the real number in hand.

That requirement has arrived, and not because of a count.

**A tenant id is runtime data.** Tenants are created through the HQ console with
generated UUIDs. A deployment-host cron schedule is static configuration written at
build time. There is no moment at which the schedule could know the ids, so a
per-tenant cron list is not "verbose at scale" — it is **unwritable**, and every new
client would need a redeploy before any of its deadlines ever fired.

Two clients now declare scheduled work: Kent's declares a `frequent` prep-breach
sweep, and plywood a `daily` low-stock sweep. Neither runs in a deployed
environment today. A capability that declares a cadence and never runs is worse
than one that declares nothing, because the screen says a manager will be told and
the manager is not told.

## Decision

**A machine trigger holding the scheduler secret may enumerate tenants, for the
sole purpose of dispatching due work.**

Concretely:

1. A new SECURITY DEFINER function, `verity.scheduler_tenant_ids()`, returns the
   ids of tenants that have **at least one active capability activation**. It
   returns ids and nothing else — no names, no counts, no rows of tenant data.
2. `POST /api/scheduled` accepts `?tenant=all`. With it, the route enumerates
   through that function and runs the requested cadence for each tenant **inside
   `withTenant`**, exactly as the single-tenant path does. There is no privileged
   path around tenancy for the work itself.
3. Everything else about ADR-015 stands: the secret is compared in constant time,
   a missing secret returns 503 rather than running unauthenticated, and failure
   shapes are identical so an attacker learns nothing from which half was wrong.

## Why this is not a fourth operator projection

ADR-013's three cross-tenant reads exist so a **person** — a platform operator —
can see across clients. Each is gated on that person holding operator authority in
the platform tenant, and each returns client-identifying data to a screen.

This is different in the two ways that matter:

- **The caller is a machine, not a person.** The gate is a deployment secret, and
  nothing about a signed-in human's authority is consulted or granted.
- **Nothing crosses.** The function returns ids so the route can re-enter each
  tenant's own scope. No tenant's data is read outside its own scope, no data from
  one tenant reaches a request about another, and nothing is returned to a browser.

An id is the minimum that dispatch requires. Returning the tenant list to a screen
would be an operator projection and would need ADR-013's gate; this deliberately
cannot do that, because it returns nothing a screen would want.

## Consequences

- One cron entry per cadence, not per client. A new client's schedules work the
  moment its capabilities are activated, with no redeploy.
- The response reports per-tenant outcomes to the scheduler, which is authenticated
  and is the only thing that can act on a failed unit.
- **A slow tenant delays the ones after it.** Dispatch is sequential, because
  parallel fan-out would multiply concurrent database connections by the tenant
  count against a pooled database. When that becomes the constraint, the fix is a
  queue, and that is a further decision with its own evidence.
- The enumeration is one function with one grant. Withdrawing this decision is
  dropping that function; nothing else depends on it.

## What was rejected

**Hard-coding tenant ids in `vercel.json`.** Unwritable, as above — the ids do not
exist when the file is written.

**Letting the route read the `tenant` table directly.** It would work only because
the runtime role can see the table, which is the kind of accident that makes an
isolation boundary depend on nobody noticing. A named function with a stated
purpose can be reviewed, granted and revoked.

**A worker process that polls.** A second thing to deploy and supervise, for work
that a cron and an HTTP request already do. ADR-015 rejected it on the same
grounds and nothing has changed.

**Opening enumeration to signed-in users.** Nothing in either client's requirements
asks a person to see across tenants outside HQ, and ADR-013 already covers the case
where one does.
