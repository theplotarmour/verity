# ADR-018 — Extract a generic Trading capability out of plywood

**Date:** 2026-09-04
**Status:** ACCEPTED
**Supersedes:** the "wait for Tasks 72/73 to be settled" gate recorded in
`taskplans/74_erpclaw_capability_selling.md` and
`taskplans/75_erpclaw_capability_buying.md`, for the specific case of
plywood's own trading engine only — not the broader claim that a second
client alone justifies extracting a platform primitive.

## Context

A second client — an auto-parts trader — is now concretely arriving.
The product owner asked whether the `plywood` capability should simply be
renamed `trading`.

An earlier session had already analyzed this exact fork, in
`erpclaw-prd/05-verity-extraction-plan.md` and taskplans 74 (selling), 75
(buying), 76 (payments). Their documented conclusion was to wait: "General
selling should not replace plywood until a deliberate extraction refactor
is planned," and buying "should remain client-private in plywood until a
second client proves generic reuse" — but taskplans 74/75 tightened that
gate further, to Tasks 72/73 being "settled" (real production use, not
merely built), explicitly because "second client exists" alone was judged
too weak a signal, and because of a named anti-pattern: "one client's need
means platform primitive."

This ADR exists because that gate is being crossed deliberately, not
skipped past. The decision was surfaced to the product owner directly,
with the conflicting documented guidance quoted in full, before
proceeding — see the session transcript of 2026-09-04. The product owner
chose to override the gate, given the second client is no longer
speculative.

An audit of the `plywood` module (13,700 lines, 29 `Plywood*` Prisma
models, 184 distinct `verity.plywood.*` entity/config/command keys) found
that **28 of 29 models are already fully generic in shape** — party
records, purchase/sales order lifecycle, invoicing, GST tax math
(`computeInvoiceTax`, `resolveTaxRate` — both HSN-keyed and
place-of-supply-keyed, not board-keyed), payments, ledger, accounting
period close, stock ledger/balance. None of it references a board
dimension. Only `PlywoodProduct`'s dimension/grade columns
(`thicknessTenthMm`, `widthTenth`, `heightTenth`, `sizeUnit`, `grade`,
`category`, `sheetWeightGrams`) and `product.ts`'s taxonomy rules
(`CATEGORY_RULES`, fixed-size locks, thickness-required-by-category) are
genuinely plywood-specific — an auto-parts trader needs part
number/OEM/fitment instead, which exists nowhere in the module today.

This is materially different from the situation taskplans 74/75 were
written against: those taskplans worried about extracting a *guessed*
abstraction before any second implementation existed to prove what's
actually shared. Here, the audit found the sharing already accidentally
happened — plywood's engine was already written generically, just
branded with plywood's name throughout. The risk the gate exists to
prevent (forcing a wrong abstraction from a single example) does not
apply to the 28 generic models; it fully applies to `PlywoodProduct`'s
dimension fields, which is why those are *not* generalized by this
decision — they stay plywood-owned.

## Decision

**Split `plywood` into two capabilities:**

1. **`trading`** (`verity.capability.trading`, `src/server/capabilities/trading/`)
   — the generic engine: parties, purchase/sales orders, invoicing, GST
   tax, payments, ledger, accounting periods, stock ledger/balance,
   business profile/GST registration, reporting. Renamed `Trading*`
   Prisma models, `verity.trading.*` entity/config/command keys.

2. **`plywood`** (`verity.capability.plywood`, unchanged id) — shrinks to
   own only `PlywoodProductDetail` (the dimension/grade fields, 1:1 with
   the generic `TradingProduct` via `productId`), `product.ts`'s taxonomy
   rules, and plywood's own navigation/UI copy. Declares a dependency on
   `trading` via `CapabilityDefinition.dependencies` — the same
   DB-trigger-enforced mechanism every other capability prerequisite
   already uses (LOCATION/ASSET/EVIDENCE ahead of PLYWOOD).

A future auto-parts capability gets its own `AutoPartsProductDetail`
table the same way, depending on `trading` directly rather than on
`plywood`.

**Entity/command key strings change (`verity.plywood.x` →
`verity.trading.x`) for the 24 generic entities only.** This is a data
migration for existing `Permission.entity` rows (rewritten forward — RBAC
control data, not history) but explicitly **not** for
`Activity`/`DomainEvent.commandKey` history, which stays append-only per
this project's own audit-trail principle; `vocabulary.ts`/`label.ts`
instead carry both old and new key strings mapped to the same human
labels.

**Existing UI code is not touched.** `plywood/index.ts` becomes a thin
composition layer that calls `registerTradingCapability()` and
re-exports everything `trading` exports, so the ~19 UI files that
`import { X } from "@/server/capabilities/plywood"` keep compiling
unchanged. The extraction is invisible from the UI layer by construction.

## Consequences

- The next trading-shaped client (auto-parts, and whatever comes after)
  builds on `trading` directly, writing only its own product-detail
  extension and command/UI layer — not a second copy of order-to-cash.
- `taskplans/74_erpclaw_capability_selling.md`,
  `75_erpclaw_capability_buying.md`, `76_erpclaw_capability_payments.md`
  are superseded for the parts of their scope this ADR actually covers
  (party records, order lifecycle, payments) — their remaining scope, if
  any beyond what `trading` now provides, stays open and un-promoted.
- The anti-pattern taskplans 74/75 warn against — guessing a shared
  abstraction from one example — still stands as a real risk for
  anything *not* already proven generic by this audit. This ADR does not
  license extracting `PlywoodProductDetail`'s taxonomy, or anything not
  explicitly listed as moved, ahead of a second real implementation.

## What was rejected

**Renaming `plywood` in place, keeping the schema as-is.** Cosmetic only
— would leave `grade`/`thicknessTenthMm` columns on a table now named
generically, misleading the first engineer who reads it for an
auto-parts client, and misleading in the other direction too (a
`TradingProduct` that still requires a plywood grade).

**Deferring entirely, per the original taskplan 74/75 gate.** Would have
been the conservative default; overridden here on the product owner's
explicit, informed decision, documented above, because the second client
is concrete rather than speculative and the audit found the abstraction
already exists rather than needing to be guessed.

**Rewriting `Activity`/`DomainEvent.commandKey` history to the new key
strings.** Rejected the same way this project already treats
`plywood_ledger_entry` as append-only: a past fact recorded under the old
key is still the true record of what happened under that key at the
time; the label map is where old and new keys reconcile for display, not
the history itself.
