# Architectural Decision Record

## ADR-003: Work Order Terminal States

*   **Decision ID**: ADR-003
*   **Question**: How is the terminal state path and archiving logic structured for `Work`?
*   **Context**: Mismatch between linear flows ending at `Closed` vs separate operational completion states.
*   **Affected Concepts**: `Work`, `SLA`, `Invoice`
*   **Evidence**: Odoo MRP workorder stages; project task stage changes.
*   **Evidence Location**: odoo/addons/mrp/models/mrp_workorder.py
*   **Options**:
    *   *Option A*: Direct flow ending at Closed.
    *   *Option B*: Separate execution terminal (`Completed`) from administrative/business closure (`Closed`).
*   **Recommendation**: Option B.
*   **Status**: `ACCEPTED`
*   **Owner**: Product Owner
*   **Resolution**: Adopt Option B. `Completed` represents the operational/execution terminal state. `Closed` is a decoupled administrative/business closure state. Billing/invoicing is one potential path to business closure, but not the definition of `Closed`. Once a Work Order is in the `Closed` state, the platform invariant `INV-002` locks it permanently to preserve history.
*   **Supersedes**: None
*   **Superseded By**: None
*   **Confidence**: `HIGH`
