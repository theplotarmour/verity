# Architectural Decision Record

## ADR-025: Apple-Craft Component Pattern Library (six named patterns)

*   **Decision ID**: ADR-025
*   **Question**: Does Verity adopt a named, citable set of reusable component patterns for the Apple-craft direction ADR-024 started, or does each page invent its own shape for actions, stats, workspace switching, charts, task lists, and AI surfaces?
*   **Context**: ADR-024 settled material, accent, and motion — the *substrate*. It deliberately did not settle component *shape*: what a primary-action control looks like, how a stat tile presents a number, how a workspace switcher reads, how a chart communicates a hovered value, how a task list groups by filter, how quick actions are offered, how an AI assistant invites a first question. Two reference screenshots supplied 2026-09-18 (Home dashboard, light + dark) show a coherent, Apple-adjacent answer to all seven — consistent enough across both themes to read as one design system's output, not one-off styling. Per `CLAUDE.md`'s own rule ("every concrete technology choice must cite its authority"), these patterns need a name and a citation before the next page can reuse them correctly instead of re-deriving something similar-but-different.
*   **Affected Concepts**: New reusable primitives layered on top of existing ones — none of the six patterns below replace an existing primitive's authority, they compose it. `Button` (ADR-024's press-state), `OverflowMenu`, `Stat`/`StatRow`, `OrganizationSwitcher`, `charts.tsx`, `TaskPanel`/`WorkQueuePanel`'s existing filter-chip idiom (Task 114 P0.1), `AgentChatDock`. **Not affected**: any command, query, entity, or authorization boundary — this ADR is presentation composition only, same category as ADR-011/023/024.
*   **Evidence**: Two reference screenshots, 2026-09-18 (Home dashboard, light + dark), supplied by the product owner with the explicit instruction to read them for UX structure, not the blue accent shown ("dont focus on colors... just focus on cover all kinds of ux"). Cross-referenced against the `apple-design` skill (WWDC "Designing Fluid Interfaces" / "Principles of Great Design") for which parts of the shown structure map to a named Apple craft principle rather than being arbitrary.
*   **Evidence Location**: This session's conversation transcript, 2026-09-18; `taskplans/115_apple_design_system_governing_docs_overhaul.md` (the taskplan this ADR executes item 1 of).
*   **Options**:
    *   *Option A*: Treat the reference screenshots as inspiration only — no named patterns, each page's author decides independently how to build a stat tile, a create action, etc.
    *   *Option B*: Name and bind the six patterns below as canonical, citable component patterns — implemented once each as shared primitives, reused everywhere a page needs that shape.
    *   *Option C*: Name the patterns but bind them only to Home/Settings (Task 111's original scope), leaving other capabilities free to keep their existing shapes.
*   **Recommendation**: Option B.
*   **Status**: `ACCEPTED`
*   **Owner**: Product Owner
*   **Resolution**: Adopt Option B. Six patterns, each with its own binding rule:

    1. **Split primary action** — a filled `Button` with an attached chevron that opens a menu (reuse `OverflowMenu`'s popover, not a new one) of related creation actions. Bind: any page currently showing exactly one "+ Add X" button where the same capability already exposes 2+ creation commands (e.g. Outreach: prospect / task / meeting) upgrades to this; a page with genuinely one creation path stays a plain `Button` — this pattern is not mandatory decoration.
    2. **Icon-chip stat tile** — circular icon-chip (`bg-accent-subtle` + `text-accent-ink`, tint only per ADR-024, never a filled tile background) + label + large number + delta-vs-prior-period + a per-tile `OverflowMenu`. Bind: replaces bare `Stat`/`StatRow` wherever a page shows 3+ headline metrics side by side; a single inline stat (e.g. a detail page's stage badge) is not this pattern.
    3. **Workspace-switcher card** — `OrganizationSwitcher`'s existing logic, presented as a bordered card (not a bare trigger) at the sidebar foot, above the identity/`ProfileMenu` control. Bind: `ShellChrome` only — this is shell chrome, not a per-page pattern.
    4. **Chart card with live tooltip** — hovering the chart surfaces every series' exact value at that x-position in a small solid tooltip (dense content, `.verity-solid` per ADR-024 — a tooltip is read text, not chrome). Bind: `charts.tsx`'s shared line/area chart component; every consumer inherits it automatically, no per-page work.
    5. **Filter-chip task/queue rows** — count-chips (`All`/`High`/`Medium`/`Low` or capability-appropriate equivalents) above a row list, each row carrying an inline status/priority pill + a due/date column. Bind: generalizes Outreach's existing `WorkQueuePanel` chip idiom (Task 114 P0.1) into a shared primitive; any future task/queue-shaped list reuses it instead of re-deriving chips.
    6. **AI-assistant suggested-prompt rows** — full-width tappable rows (not a bulleted list) offering 3-4 capability-aware starting questions, shown in `AgentChatDock`'s empty/idle state above the input.

    Every pattern above composes existing primitives and existing ADR-024 material/accent/motion rules — none introduces a new material, a new accent usage, or a new command. A component built to one of these patterns cites `Authority: ADR-025 [pattern name]` the way any other concrete choice in this repo does.

    Option A was rejected because it's the status quo this ADR exists to fix — "inspiration only" is how the platform already ended up with `WorkQueuePanel`'s chip idiom never generalized past Outreach, the exact gap pattern 5 above closes. Option C was rejected because nothing about these six patterns is Home/Settings-specific — pattern 5 in particular was *discovered* in a different capability (Outreach) — restricting them to Task 111's original two surfaces would re-fragment the platform along capability lines, which is what the platform-foundation posture (`CLAUDE.md`'s own "standardize the foundation, not every behavior") argues against.
*   **Supersedes**: none — this is additive to ADR-011/012/023/024, not a replacement of any of them.
*   **Superseded By**: none (current)
*   **Confidence**: `MEDIUM` — grounded in explicit product-owner-supplied reference evidence for structure, but the specific binding rules (when a page "upgrades" to a pattern vs. stays as-is) are this session's own synthesis, not separately confirmed line-by-line. Expect refinement as each pattern is actually built and reviewed, same caveat ADR-024 carries.
