# Architectural Decision Record

## ADR-010: Specification Status Taxonomy

*   **Decision ID**: ADR-010
*   **Question**: What does the `Status` field on a specification requirement mean, and which values withhold permission to implement?
*   **Context**: Every requirement in `verity-spec/` carries a `Status`. The scheme was in use across 3,565 annotations before it was ever defined — `[UNKNOWN_REASON: FUTURE_CAPABILITY]` alone appears 1,096 times — and no document in the Bible, the specification or the implementation handoff said what any value meant. The ambiguity was not academic: `[UNKNOWN_REASON: FUTURE_CAPABILITY]` could be read as *ratified but not yet built* or as *not yet ratified, do not build*, and those readings disagree about whether roughly a third of the corpus is safe to implement. The platform foundation build surfaced this as a blocker, since the tenancy, identity, authorization, entity, command, state, event, audit, workflow, capability and sync requirements are predominantly marked that way.
*   **Affected Concepts**: Every requirement in `verity-spec/`; the implementation gate in `implementation/13-conformance/`
*   **Evidence**: Three observations from the corpus itself constrain the answer.

    First, the field's own name. The unresolved values are `UNKNOWN_REASON: <reason>`, and each reason — `FUTURE_CAPABILITY`, `SOURCE_UNAVAILABLE`, `RESEARCH_REQUIRED`, `INTENTIONALLY_DEFERRED` — is a reason a *citation* could not be supplied, not a reason a requirement is doubted.

    Second, the distribution. `[UNKNOWN_REASON: …]` appears 1,834 times in `verity-spec/` and **zero** times in `verity-bible/`, which annotates sections with `[FACT]`, `[DECIDED]`, `[INFERRED]` and `[PROPOSED]` instead. A ratification marker would be expected in the constitutional document; a provenance marker on individual requirements would not.

    Third, where the rare values cluster. All 6 `INTENTIONALLY_DEFERRED` and all 10 `RESEARCH_REQUIRED` annotations sit in `00_governance/` — requirements about the corpus's own governance, which have no external reference system to trace to. That is precisely the pattern a provenance marker produces and not one a ratification marker would.

    Fourth, and decisively, requirements marked `FUTURE_CAPABILITY` proved fully implementable. Around forty of them were implemented during the foundation build without encountering ambiguity, and `PLA-TEN-006` is marked `[DECIDED]` while `PLA-TEN-001` through `005` beside it are marked `FUTURE_CAPABILITY` despite being written in identical prescriptive terms.
*   **Evidence Location**: `verity-spec/` corpus-wide annotation counts; `verity-spec/01_platform/tenancy.md`; `verity-spec/00_governance/`.
*   **Options**:
    *   *Option A*: Treat `Status` as a ratification gate — only `[DECIDED]` and `[FACT]` may be implemented.
    *   *Option B*: Treat `Status` as a provenance record describing how the requirement's content was established, gating implementation only where a value explicitly says the underlying question is open.
    *   *Option C*: Deprecate the field and re-annotate the corpus.
*   **Recommendation**: Option B.
*   **Status**: `ACCEPTED`
*   **Owner**: Product Owner
*   **Resolution**: Adopt Option B, defined in full in `00_governance/status-taxonomy.md`.

    `Status` records **provenance** — what evidence stands behind a requirement — and not ratification or implementation state. Ratification is expressed by the authority hierarchy and by ADRs; implementation state lives in `15_traceability/`.

    Exactly one value gates implementation: `[UNKNOWN_REASON: INTENTIONALLY_DEFERRED]`, which says the question behind the requirement is deliberately open and must be escalated rather than built. It applies to six annotations. Every other value permits implementation of an unambiguous requirement.

    `[INFERRED]` carries one ordering rule: it is the weakest resolved value, so an inferred requirement yields to a `[FACT]` or `[DECIDED]` one rather than being reconciled locally.

    Option A was rejected because it would retroactively invalidate the platform foundation, and because it attributes a meaning to the field that its own naming contradicts. Option C was rejected as disproportionate: the annotations are consistent and useful once read correctly, and re-annotating 3,565 of them would introduce far more risk than defining the seven values they already use.

    The value set is closed. A new `Status` value requires an ADR, because an undefined value reproduces exactly the condition this decision was made to end.
*   **Supersedes**: None
*   **Superseded By**: None
*   **Confidence**: `HIGH`

---

## Consequences

*   The implementation blocker recorded during the foundation build is closed. `[UNKNOWN_REASON: FUTURE_CAPABILITY]` does not withhold permission to implement.
*   Conformance checking can treat `INTENTIONALLY_DEFERRED` as a hard stop and every other value as permissive.
*   `00_governance/status-taxonomy.md` becomes the reference for the field; `decision-framework.md` continues to govern ADR and DEC-REQ lifecycle, which is a separate concern.
*   No requirement text changes as a result of this decision.
