# ADR-021: Capability pins are runtime contract versions

- Status: Accepted
- Date: 2026-09-16
- Scope: capability execution and deployment readiness

## Decision

Verity currently ships one handler implementation of each capability in one
application artifact. Therefore `TenantActivation.pinnedVersion` is an enforced
contract/data version, not an independent per-tenant code deployment selector.

Every execution surface must deny when an active tenant pin is absent or differs
from the loaded `CapabilityDefinition.version`. Deployment readiness must also
fail when any active tenant in the database has such a mismatch. The global
readiness count is exposed only through a purpose-specific, no-argument
`SECURITY DEFINER` function with PUBLIC execution revoked; it does not grant the
web role a cross-tenant row-reading primitive.

Activation pins the currently loaded definition version. A future upgrade
service may move a tenant through preflight/apply/verify and change the pin only
after its version-specific config/data checks succeed. Until that service and
its rollback rules exist, operators must not describe the system as supporting
mixed handler versions or independent tenant rollback.

## Consequences

- A stale pin can no longer execute newer code silently.
- A missing pin fails closed instead of being interpreted as “latest.”
- Deployments with incompatible existing activations are non-ready before the
  affected capability is used.
- Exact-version enforcement is intentionally stricter than a speculative SemVer
  range. Compatible ranges require explicit release metadata and tests.
- WP-11A remains partial: durable upgrade operations, tenant migrations, mixed
  supported contract versions, and rollback boundaries are not yet built.
