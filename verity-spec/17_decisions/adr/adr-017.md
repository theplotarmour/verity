# ADR-017 — The AI agent channel carries no elevated authority

**Date:** 2026-09-03
**Status:** ACCEPTED
**Supersedes:** nothing. Ratifies behavior already present in `command.ts`
and `policy.ts`; changes no code.

## Context

`taskplans/84_verity_ai_agent_system.md` records a design conversation
about giving Verity a native AI agent that can add records, execute
commands, and act across capabilities. The obvious danger in a system
like that is a service account or an "AI can do more than the user who
invoked it" carve-out — quietly trusting a program more than the person
using it.

The platform's own authorization runtime already forecloses this, and did
so before this ADR was written. `policy.ts` defines a fourth caller
channel, `PolicyChannel: "human" | "api" | "job" | "agent"`, added in
anticipation of exactly this case:

> "An AI agent added in Phase 9 would have become a fourth caller with a
> fourth set of habits, which is how an authorization model rots — not by
> being wrong, but by being asked in four different ways."
>
> "THE CHANNEL IS RECORDED, NEVER CONSULTED. The dangerous reading of 'AI,
> API, UI and human actions share one model' is a system that quietly
> trusts a service account more than a person."

`policy-engine.test.ts` already asserts identical authorization verdicts
across all four channels for the same actor and request. There is no code
path today by which the `"agent"` channel receives a grant a `"human"`
caller in the same seat would not.

## Decision

**The AI agent channel authenticates and authorizes as the calling
human's own `ActorContext` — same tenant, same membership, same role,
same grants, same `enforcePolicy()` gate every other caller passes
through. `channel: "agent"` is recorded on the authorization decision and
the audit trail for provenance only, and is consulted by no authorization
rule. There is no service-account, elevated, or agent-specific authority
path for AI-issued commands or queries, now or later, without a fresh
ADR superseding this one.**

This decision changes no code — it ratifies `command.ts`/`policy.ts`'s
existing behavior as constitutional, the way ADR-013 ratified a security
model rather than inventing one.

## Consequences

- `taskplans/84_verity_ai_agent_system.md`'s six implementation areas
  (tool-manifest generation, confirmation-class tagging, actor-scoped
  tool visibility, grounding enforcement, query-channel audit parity, the
  chat surface) may proceed — this ADR was the gate on all six.
- Any future request to give the agent broader reach than the invoking
  human — a background job acting with no human in the loop, a
  platform-level automation — is explicitly **not** covered by this
  decision and needs its own ADR. `taskplans/95_verity_ai_long_term_
  vision.md` Phase 6 (bounded autonomous operation) is flagged there for
  exactly this reason.
- No new database role, no new permission scope, no change to
  `resolve_permissions` or `enforcePolicy`.

## What was rejected

**A dedicated `verity_agent` service identity with its own grants.**
Rejected for the same reason ADR-013 rejected a `BYPASSRLS` operator
role: any bypass of the actor-scoped authorization path is a hole whose
size grows with what gets added behind it, regardless of how carefully
it starts. The agent needs no authority a human in the same seat doesn't
already have — if it did, that would be an argument to change the human's
role, not to give the agent a side door.

**Treating `channel` as an authorization input.** Considered and rejected
by `policy.ts` before this ADR existed; restated here because it is the
single property this whole decision rests on. `channel` may inform UI,
logging, and audit — never a grant.
