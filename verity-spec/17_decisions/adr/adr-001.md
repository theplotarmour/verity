# Architectural Decision Record

## ADR-001: Party Lifecycle State Decoupling

*   **Decision ID**: ADR-001
*   **Question**: What is the canonical lifecycle and state structure of the `Party` primitive?
*   **Context**: `concept-inventory.md` defined the lifecycle starting at `Prospect` (CRM focus), while `primitive-validation.md` defined it starting at `Invited` (workforce focus).
*   **Affected Concepts**: `Party`, `User`, `Membership`
*   **Evidence**: Odoo uses `res.partner` directly with an active flag, while identity managers (e.g. Keycloak) manage registration states.
*   **Evidence Location**: Keycloak UserModel registration state; Odoo Partner active flag.
*   **Options**:
    *   *Option A*: Force a single universal state machine (e.g., Prospect or Invited).
    *   *Option B*: Decouple capability-specific profiles and roles from the platform primitive.
*   **Recommendation**: Option B.
*   **Status**: `ACCEPTED`
*   **Owner**: Product Owner
*   **Resolution**: Adopt Option B. The platform defines the basic `Party` primitive representing identity. Sub-capabilities (like CRM and Workforce) define separate domain roles/profiles with their own lifecycles (e.g., `Prospect` and `Invited` respectively) that map to the platform's stable contracts. This prevents single-person identity duplication while allowing specialized domain workflows.
*   **Supersedes**: None
*   **Superseded By**: None
*   **Confidence**: `HIGH`
