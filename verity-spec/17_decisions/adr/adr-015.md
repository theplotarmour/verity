# Architectural Decision Record

## ADR-015: Scheduled Work Trigger

*   **Decision ID**: ADR-015
*   **Question**: What invokes `runDueWork`, and how is that invocation authenticated?
*   **Context**: The schedule contract has been complete and tested since the foundation gate: a capability declares recurring work as a cadence, and `runDueWork` executes each unit under `withTenant`. Nothing called it. `PLATFORM-FREEZE.md` recorded that deliberately — *"A contract with no provider is a decision that has been made. A provider chosen with no requirement is a decision that has been guessed"* — and named this as one of three bindings waiting for a real requirement.

    Kent's is that requirement. Kitchen prep clocks start and stop correctly from state categories, and `sweepBreaches` flips an overdue clock to `Breached` and emits `verity.sla.breached`. With nothing invoking it, a manager is never told a dish is late **while it is still late**, which is the only moment the information is worth anything.

    The mechanism is an implementation decision. The **authentication of the trigger** is a security boundary, and that is why this ADR exists rather than a commit message.
*   **Affected Concepts**: `ScheduleContribution`; `runDueWork`; SLA breach sweep; notification drain; deployment configuration; `verity.capability.dinein`
*   **Evidence**: Three properties of the existing contract decide most of this.

    First, **cadences are deliberately not cron strings**. A capability declares that work must happen "frequently"; it does not know whether production runs on a host scheduler, a worker loop, or something not yet chosen. Any trigger that satisfies the cadence is therefore equivalent from the capability's side, and the cheapest one wins until something demands otherwise.

    Second, **`runDueWork` already runs each unit under `withTenant`**. There is no privileged path around tenancy for background work, and nothing about binding a trigger needs one.

    Third, **the units are idempotent by construction**. `sweepBreaches` only marks clocks past their deadline that are not already breached. Every real scheduler retries, and the contract was written on that assumption rather than on a promise no provider makes.
*   **Evidence Location**: `src/server/platform/contribution.ts` (`ScheduleContribution`, `runDueWork`); `src/server/platform/sla.ts` (`sweepBreaches`); `implementation/PLATFORM-FREEZE.md`; `KentsRestaurant.md` §10, §17 D2; `implementation/decisions-d11-d7-d2.md`
*   **Options**:
    *   *Option A*: The deployment host calls an authenticated route on a schedule.
    *   *Option B*: A long-running worker process calls `runDueWork` in a loop.
    *   *Option C*: A managed queue or workflow vendor.
*   **Recommendation**: Option A.
*   **Status**: `ACCEPTED`
*   **Owner**: Product Owner
*   **Resolution**: Adopt Option A. `POST /api/scheduled` is the trigger.

    Option B adds a second process to deploy and supervise for work that has no sub-minute requirement. Option C adds a dependency and a bill so that one restaurant's prep clocks can have retries the contract already tolerates without them. Both remain available: replacing the trigger changes nothing any capability can see, which is precisely what the cadence abstraction was built to allow.

    ### How it is authenticated

    - A **shared secret** in `CRON_SECRET`, supplied as `Authorization: Bearer …`. It is compared with `timingSafeEqual`; a plain equality check on a secret leaks its length and then its content to anyone willing to measure.
    - **Absent configuration refuses the request** (503) rather than running unauthenticated. A scheduler endpoint with no secret is a way to make the platform do work on demand from outside, and a missing environment variable is not a reason to become one.
    - **Failures are indistinguishable.** A wrong secret and a missing tenant return the same shape, so a caller learns nothing about which half was wrong.
    - The secret is **deployment configuration, never source**, and is rotated the way any other credential is.

    ### Tenancy

    **The caller names one tenant per call.** Enumerating tenants inside the route would be a cross-tenant read, and ADR-013 lists exactly three of those, each a deliberate and reviewable act. A cron endpoint does not get to add a fourth on the way past.

    One schedule entry per client is honest at present scale. When there are enough clients for that to be unmanageable, that is a real requirement and it can be answered then — with a number in hand, by extending ADR-013's enumerated surface rather than by quietly widening this route.

    Active capabilities are read **inside the named tenant's own scope**, under its own policies, and every unit runs under `withTenant`. Background work has no privileged path around tenancy and does not acquire one here.

    ### What this does not decide

    Storage driver and notification transport remain unbound. Neither is required by Kent's: photos are optional in v1, and in-app notifications are visible on surfaces that already poll. They wait for the requirement that forces them, exactly as this one waited.
