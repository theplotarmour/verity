# Architectural Decision Record

## ADR-009: Platform State Category Taxonomy

*   **Decision ID**: ADR-009
*   **Question**: What is the fixed, platform-level set of `StateCategory` values that the engine reasons about?
*   **Context**: MET-STA-001 requires state categories to be "fixed, platform-level enums that dictate core engine behavior", and decouples them from tenant-facing status labels (MET-STA-002) so that SLA clocks and progress can be computed consistently while tenants rename states freely (MET-STA-004). But the categories it lists as examples — `DRAFT`, `SCHEDULING`, `EN_ROUTE`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED` — are Work-domain values. `EN_ROUTE` and `SCHEDULING` describe a dispatched field-service job; they are the Work capability's *states*, not platform categories. Placing them in the platform core would make the core field-service specific, which contradicts Bible V1 §3 ("standardize the foundation, not every behavior") and reproduces exactly the domain leakage the no-legacy policy forbids — `Department`-as-production-stage is banned for the same reason. The platform therefore needed a category set the specification mandates the existence of but never enumerates in domain-neutral terms.
*   **Affected Concepts**: `State`, `Transition`, `SLA`, `Work`, every stateful entity
*   **Evidence**: Plane's state-category concept, from which MET-STA-001 is traced, separates a small fixed set of *behavioural* groupings from the freely-named states a team configures inside them. The behaviour the engine needs is limited and identifiable: whether a clock runs, whether the record is open, whether it is finished, and whether finishing was success or abandonment.
*   **Evidence Location**: Plane state-group model; MET-STA-004's own clock semantics (`Running`, `Paused`, `Stopped`).
*   **Options**:
    *   *Option A*: Adopt the specification's example list verbatim as the platform enum.
    *   *Option B*: Define a behavioural, domain-neutral set derived from what the engine must actually decide, and let capabilities express domain states as their own `StateDefinition` rows bound to those categories.
    *   *Option C*: Let each capability declare its own categories.
*   **Recommendation**: Option B.
*   **Status**: `ACCEPTED`
*   **Owner**: Product Owner
*   **Resolution**: Adopt Option B. The platform category set is fixed at six values, chosen because each one changes what the engine does rather than what a domain calls it:

    | Category | Engine meaning | SLA clock (MET-STA-004) |
    |---|---|---|
    | `Draft` | Not yet started; the record exists but no commitment has been made | Not started |
    | `Pending` | Open, waiting on something external before work can proceed | Paused |
    | `Active` | Work is happening | Running |
    | `Blocked` | Open but halted by an exception | Paused |
    | `Completed` | Terminal, having succeeded | Stopped |
    | `Cancelled` | Terminal, having been abandoned | Stopped |

    `Pending` and `Blocked` both pause the clock but are kept distinct because they differ in whose action resumes them — `Pending` waits on an external party, `Blocked` waits on an exception being resolved — and exception handling and reporting need to tell them apart. `Completed` and `Cancelled` are both terminal and both stop the clock, but conflating them would make it impossible to compute a completion rate.

    The specification's example values map onto this set without loss: `DRAFT` → `Draft`, `SCHEDULING` → `Pending`, `EN_ROUTE` → `Active`, `IN_PROGRESS` → `Active`, `COMPLETED` → `Completed`, `CANCELLED` → `Cancelled`. A capability that wants `EN_ROUTE` and `IN_PROGRESS` to be visibly different declares two `StateDefinition` rows both bound to `Active`; the engine treats them identically, which is correct, because the clock does not care whether the technician is driving or working.

    Option A was rejected because it puts field-service vocabulary in the platform core. Option C was rejected because it defeats the purpose of a category: if every capability defines its own, the engine cannot compute an SLA or a progress figure across capabilities, which is the one thing MET-STA-001 exists to enable.

    Terminal categories carry INV-002: a record whose state is bound to `Completed` or `Cancelled` is permanently read-only.
*   **Supersedes**: None
*   **Superseded By**: None
*   **Confidence**: `HIGH`

---

## Consequences

*   `StateCategory` is closed. Adding a seventh value is a platform architecture decision requiring a new ADR, not a capability's choice.
*   Capabilities express domain vocabulary as `StateDefinition` rows and tenant vocabulary as `TenantStatusLabel` rows. Neither can introduce a category.
*   SLA and progress computation reads `category` only, never `key` or `label`, so renaming a state can never change behaviour.
*   `isTerminal` on a `StateDefinition` must agree with its category: only `Completed` and `Cancelled` may be terminal.
