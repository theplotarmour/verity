# ADR-020 — Complete OIDC browser identity is the initial on-prem profile

**Date:** 2026-09-16
**Status:** ACCEPTED

## Context

Verity could verify OIDC bearer/id tokens but could not initiate or complete a
browser login. The on-prem documentation nevertheless presented OIDC as an
identity-provider replacement. Task 108 requires one honest initial profile:
either a complete OIDC browser relying party or a permanent Supabase-auth
dependency.

## Decision

The initial on-prem identity profile is a complete OIDC browser relying party.
It uses authorization code with PKCE, signed short-lived transaction cookies,
random state and nonce, an exact configured redirect URI, strict discovery and
token validation, a database replay ledger, and a bounded Verity application
session. API bearer verification remains separate.

Accounts are pre-provisioned. A verified token never creates a user,
membership, tenant, or role, and email/domain claims never link identity.
Password reset and MFA belong to the IdP. The first supported mapping retains
the existing UUID `User.authUserId` contract, so the configured principal claim
must be a stable UUID.

## Consequences

- Supabase is not required for OIDC deployments.
- Operators must register the exact Verity callback URI and provision the
  principal UUID before login.
- Login transactions are single-use across restarts through the database replay
  ledger; only a state hash is stored.
- Local sessions are HttpOnly, SameSite=Lax, Secure in production, and have a
  configured absolute lifetime.
- Recovery UI is provider-specific: OIDC users are directed to their IdP;
  Supabase users retain Verity's enumeration-resistant reset flow.
- Full closure still requires a disposable IdP end-to-end run, key rotation,
  provider outage, and browser cookie tests against the exact release artifact.

## Rejected alternatives

- Calling bearer-only verification an interactive identity profile.
- Auto-provisioning from email, group, domain, or tenant claims.
- Storing raw authorization codes, PKCE verifiers, or tokens in the database.
- Keeping Supabase Auth as an undocumented dependency of the OIDC profile.
