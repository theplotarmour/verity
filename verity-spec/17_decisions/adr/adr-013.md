# Architectural Decision Record

## ADR-013: Global HQ Operator Security Model

*   **Decision ID**: ADR-013
*   **Question**: How does a Verity HQ operator administer every client without disabling the row-level security that enforces INV-001?
*   **Context**: D15–D18 place HQ above client organizations, which is the `Global` permission scope. `verity.resolve_permissions` deliberately filters `Global` grants out today, so such a grant may exist without silently taking effect — a fail-closed default that D15 now requires be opened, deliberately and narrowly.

    The runtime role `verity_app` is `NOSUPERUSER NOBYPASSRLS`, so it genuinely cannot see past a policy; `withTenant()` sets `verity.tenant_id` transaction-locally and with no scope set queries return nothing and writes are rejected. Any operator mechanism must survive inside that, not around it.

    The option comparison is `implementation/adr-013-proposal.md` §2–§4 and is not repeated here.
*   **Affected Concepts**: INV-001; `withTenant()`; `verity.resolve_permissions`; `TenantMembership`; command pipeline; audit; HQ console; operator identity
*   **Evidence**: The decisive finding is in the proposal §1.1. Of the seven things HQ must do, **only three genuinely span tenants** — listing clients (metadata only), the platform-wide operational view, and platform audit. The other four, which are the bulk of HQ's screens, need the *authority to enter* a tenant and then ordinary tenant-scoped operation. A mechanism sized for all seven would be far wider than the problem.

    Second: an operator whose authority is ambient rather than selected has no answer to "which tenant am I acting in" that the database can verify. That is the condition PLA-TEN-006 exists to prevent, and it rules out any shape where authority is global and context is application state.

    Third: `CLAUDE.md` already rejected a parallel authorization model once, when it refused a numeric field-permission level ladder as "a second authorization model to keep in sync with the first". An operator authority system outside roles and permissions would be that same mistake at a larger scale.

    Fourth: a `BYPASSRLS` connection for HQ recreates precisely the failure `assertRlsEnforceable()` was written to catch — every policy still present, every test still passing, and no isolation at all.
*   **Evidence Location**: `implementation/adr-013-proposal.md`; `src/server/platform/tenancy.ts`; `src/server/platform/authorization.ts`; `prisma/migrations/*_resolve_permissions*`; `CLAUDE.md` — "Authorization shape", "Database connection roles"
*   **Options**: A — operator tenant plus authorized context switching. B — operator authority orthogonal to tenancy, with `SECURITY DEFINER` reads. C — a second database role carrying `BYPASSRLS`. D — A's discipline plus a closed, enumerated set of read-only platform projections. (Full comparison: proposal §2–§3.)
*   **Recommendation**: Option D, with operator identity Shape 1.
*   **Status**: `ACCEPTED`
*   **Owner**: Product Owner
*   **Resolution**: Adopt **Option D** with **Shape 1**.

    Authority and every mutation follow Option A's rule: the operator selects one client, `withTenant()` is set to it, and the ordinary policies apply. In addition, a **fixed, enumerated, read-only** set of `SECURITY DEFINER` projections serves the three needs that genuinely span tenants, returning platform metadata and aggregates and never client business rows.

    Option C is rejected on the record: it contradicts the standing rule that a bypassing role must never carry application traffic.

### The twelve answers

1. **How does an operator authenticate?** Exactly as any user — Supabase password auth, then membership resolution. No second login path.
2. **How is operator authority represented?** As a `TenantMembership` in the platform tenant, carrying a role whose permissions are ordinary `Verb + Entity + Scope` grants. No new authorization model, and operator RBAC (support versus billing versus engineering) is free.
3. **How does an operator select a tenant?** Explicitly, by choosing a client. Never inferred, never ambient, never taken from a request payload (PLA-TEN-006).
4. **How does the selection become authoritative?** It is re-verified server-side against the operator's platform membership on every request, exactly as `setActiveMembership` re-verifies ordinary membership, and then set as the transaction-local `verity.tenant_id` GUC. The database, not the client, decides what is visible.
5. **How does RLS remain effective?** It is never bypassed for a write, nor for any read of client business data. Every operational query runs inside exactly one tenant scope under the same policies as a tenant user's.
6. **How are cross-tenant reads performed?** Only through the enumerated projections below. Each pins `search_path`, contains no dynamic SQL, returns a fixed column set, is `STABLE` and read-only, and logs its invocation.
7. **How are cross-tenant mutations performed?** They are not. There is no cross-tenant write path. A mutation happens inside one selected tenant, through `runCommand`, or it does not happen.
8. **How are these actions audited?** Mutations by the existing pipeline, which cannot be skipped. Operator-originated actions carry an `operator` marker distinguishing them from ordinary tenant activity. Each projection logs its own invocation.
9. **How does the system fail closed?** With no tenant selected, scope is unset and queries return nothing. Without the operator permission, entering a client is refused by `authorize()`, which throws rather than returning false. A projection called by a non-operator returns no rows.
10. **How is accidental tenant leakage prevented?** No query ever spans two tenants, so there is no code path along which one client's rows can arrive in another's result. The selected client is displayed persistently in HQ chrome.
11. **How are operators separated from tenant users?** The platform tenant is marked as such and is never a client. HQ routes require the operator permission; a tenant user reaching them is refused and a security event is recorded (D18).
12. **How are privileged actions distinguished in audit?** By the operator marker plus the platform-tenant membership on the audit row — queryable, not merely visible.

### The cross-tenant surface, in full

Adding to this list is a deliberate, reviewable act. It is short on purpose.

| Projection | Returns | Serves |
|---|---|---|
| Client directory | tenant id, name, status, created-at, member count | N1 — list and search clients |
| Platform operations | counts of failed operations and pending work per tenant | N6 |
| Platform audit | audit metadata across tenants, no payload bodies | N7 |

No projection returns client business rows. No projection writes.

### QO-3 — client-visible transparency

Operator actions inside a client appear in **both** that client's audit trail and the platform stream. A privileged action a client cannot see is one they cannot question.

### Consequences accepted

- Platform-wide aggregates cost a deliberate function each rather than an ad-hoc query. That is the mechanism working: widening the surface is a visible act.
- The platform tenant is a tenant that is not a client. D18 requires it be distinguishable in code, in the UI and in audit, which the marker provides.
- `resolve_permissions` continues to filter `Global` grants. Operator authority is a real membership with real permissions, not a `Global` row — so nothing about the existing resolver changes.
