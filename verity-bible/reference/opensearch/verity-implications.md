### Postpone Separate Search Cluster (PostgreSQL TSVector for v1)

Confidence: HIGH
Recommendation: ADAPT
Rationale: While OpenSearch's inverted index and vector capabilities are premium, managing a separate OpenSearch cluster introduces synchronization complexity, eventual consistency lag, and high infrastructure costs. For Verity v1, PostgreSQL's native GIN indexes, TSVector full-text search, and PostGIS geo-routing are sufficient.
If ADAPT: Verity's search engine is built directly inside PostgreSQL using PostGIS for coordinate calculations and native TSVector columns for text search. Write-ahead sync logic is deferred.
Affects Bible sections: Volume V (Data Architecture)

---

### Tenant Filtering as Cache Boundary

Confidence: HIGH
Recommendation: ADOPT
Rationale: OpenSearch separates query scoring from caching filters. In a multi-tenant application, tenant-level scoping (`tenant_id = X`) must never affect relevance scoring and should always be a strict, cached filter to prevent cross-tenant data leaks.
If ADOPT: Every search query generated by Verity enforces tenant filtering inside the database/search engine query planner at the lowest level, bypassing relevance calculation.
Affects Bible sections: Volume V (Security & Multi-tenancy)

---

### Geo-Point Indexing for Dispatching

Confidence: HIGH
Recommendation: ADOPT
Rationale: Distance sorting and radius calculations are critical for allocating jobs to field technicians. Coordinate values must be stored in a specialized geospatial format (e.g. PostGIS `GEOMETRY` or equivalent), rather than plain latitude/longitude floats, to enable spatial indexing.
If ADOPT: Verity's `Location` and `Resource` tables index spatial coordinates using coordinate geohash formats (equivalent to OpenSearch's `geo_point`), allowing fast radial queries.
Affects Bible sections: Volume II (Location model), Volume III (Scheduling & Dispatch)
