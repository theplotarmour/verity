# Verity — Phased Execution Plan

**Revision:** 3 (2026-08-26). Supersedes Revisions 1 and 2 of the same date.
**Status:** PROPOSED — final execution plan, awaiting product-owner approval.
**Authorization:** none. This document is a plan, not permission to implement. See §14.

## The central question

> **Can Verity become the production-quality foundation on which we build and operate real client
> systems?**

The definition of ready is now stricter than in Revision 2:

> **Verity must be fully usable by the Verity team through HQ — including global client
> administration — before any client-specific implementation begins.**

"Ready" is demonstrated through evidence, not appearance. Three separate verdicts must each return
YES (§13). Acceptance criteria are checkable by command where possible and by named artefact where
not. No criterion may be weakened, removed, or silently reinterpreted to make the project appear
ready.

### The correct definition

> **Steep.app is the experience and visual-quality reference for Verity.** It informs composition,
> restraint, whitespace, hierarchy, typography treatment, gradients, polish, spatial rhythm and
> premium product presentation.
>
> It does **not** define Verity's brand colour, product information architecture, enterprise
> workflows, permission model, tables, forms, dashboards, or operational interaction patterns.

### Reference hierarchy — binding

```
Verity design files  (design/ — brand sheet, theme boards, logo)
        ↓  takes precedence over
Verity product requirements  (spec, Bible, ADRs, architecture)
        ↓  takes precedence over
Steep experience reference  (design/DESIGN.md, theme.css, variables.css, tokens.json)
        ↓
Implementation
```

Where `design/` states an explicit Verity design decision, it wins over Steep.
Where neither answers an enterprise-product requirement, **Verity's product requirements and
architecture govern.**

Never:

```
Steep  →  copy website  →  force into ERP
```

### 0.6 — Database diagnosis, in strict order

Observed: `FATAL: (ECIRCUITBREAKER) too many authentication failures, new connections are
temporarily blocked` against `aws-1-ap-south-1.pooler.supabase.com`. Consequence: 19 of 21 test
files fail, **258 of 291 tests skip**. `npm run typecheck` is clean.

Per D23, infrastructure-first. Escalate only when a level disproves itself:

1. **Connectivity** — wait out the pooler cool-down, retry once. A clean connect ends it.
2. **Credentials** — if it re-trips immediately, the `verity_app` password was rotated or revoked.
   Re-issue in Supabase, update `DATABASE_URL`. Still infrastructure.
3. **Configuration** — verify `DATABASE_URL` → `verity_app`, `DIRECT_URL` → `postgres`, pooler mode
   matches Prisma's expectation. Still infrastructure.
4. **Application / test setup** — only if 1–3 pass and tests still fail.
5. **Architecture** — only if 4 disproves itself. **No architectural change under this heading
   without a written finding first.**

**The failing tests are not evidence of broken code.** They are evidence the database is
unreachable. Until 0.6 clears, every "PROVEN" claim in `implementation/` is a documented belief
rather than a verified state.

## 5. Phase 1 — Final Verity Design System

**Goal:** one locked, documented Verity visual system derived from `design/`, informed by Steep's
experience quality, governed by Verity's product requirements — with architectural history
recorded rather than overwritten.

### 5.1 — ADR-012 first

No token is edited before the ADR exists. That ordering is why the current system is internally
coherent: ADR-011 preceded `globals.css`.

**ADR-012 — Verity Visual System v2** must record: the reference hierarchy (§2); the brand-sheet
evidence (F1); the clause-by-clause ADR-011 fate table (F4) showing glass is **retained**; the
accent-default change with QB-1's answer; the dual-theme mandate; the glass placement matrix
(§5.3); the shell and scroll architecture (§5.6, §5.7); and every intentional deviation from the
boards with its reason.

`verity-bible/` is **not** edited — AMD-001 is spent and an ADR is the correct instrument.
ADR-011's `Superseded By` becomes `ADR-012 (partial — accent default only)`.
`CLAUDE.md` is updated in the same change if QB-1 confirms the accent, because leaving *"do not
replace gold with teal"* in force while shipping `#00D1B2` would put the repository's own
instructions in contradiction with its code.

### 5.2 — Foundation

Verity uses: neutral backgrounds · neutral surface hierarchy · subtle background gradients ·
controlled atmospheric effects · strong typography hierarchy · restrained borders · controlled
shadows · premium whitespace · configurable accent.

The interface must feel like a **premium business operating system**, not a conventional generic
ERP — and not a marketing page.

Explicitly:

- **Do not make every element a card.**
- **Do not make every surface glass.**
- **Do not make every section visually elevated.**
- Whitespace, alignment, hierarchy and density must still do significant structural work.

### 5.3 — Glass material system — audit and formalize, do not delete

Measured current usage: **26 references across 7 files** — `globals.css` (33 token lines),
`ShellChrome` (9), `primitives` (8), `AppearanceControls` (4), `charts` (2), `icons` (1),
`VerityMark` (1), `conformance.test.ts` (1).

The audit determines, per token and per usage, whether to **retain, rename, consolidate or
redesign**. Deletion is a possible outcome for an individual misuse, never the default.

**Where glass is appropriate:**

- elevated dashboard cards
- contextual panels
- floating controls
- selected / active navigation surfaces
- overlays and modals
- contextual information sections
- visually important but **non-dense** dashboard surfaces

**Where glass must not dominate:**

- every table row
- every form field
- every page background
- every text block
- every dense data surface
- every navigation item

**Glass must preserve:** text contrast · focus visibility · readability · performance · semantic
clarity · dark/light parity.

**Revision 2's criterion `grep -rn "glass" src/` returns 0 is deleted.** Replaced by:

> **Every glass material has a documented purpose, token, contrast behaviour and theme-specific
> implementation, and no component uses glass merely as decorative default styling.**

### 5.4 — Accent system — conceptual model corrected

**Brand identity** = the Verity name · logo / mark · typography identity · visual language ·
overall product character. **The UI accent is not part of it** (D9).

**UI accent** = a configurable product theme property.

Retain the existing infrastructure, which is architecturally sound: accent seed · generated 50–900
scale · computed contrast · presets · appearance controls · component-level consumption.

Audit so that the accent is **not hardcoded into individual components**, and verify the chain is
one coherent system (D10):

```
accent selection
      ↓
theme tokens
      ↓
components
      ↓
interactive states  (hover · active · focus · disabled · selected)
      ↓
charts / visualization
      ↓
navigation / active states
```

**Do not import Steep's palette because Steep uses it** (D3).

### 5.5 — Light and Dark — both mandatory, both designed

D7 and D8 bind. Revision 2's recommendation to remove `ThemeToggle` is **reversed**; the toggle
stays in the product shell.

Each theme is designed and tokenized independently across: background · surfaces · glass · borders
· text hierarchy · accent · semantic colours · controls · tables · charts · navigation · overlays.

**Dark is not implemented by inverting light.** The boards prove the intended approach — dark
re-renders rather than filters. The same component must remain semantically understandable in both
themes.

### 5.6 — Shell and scroll architecture

The application must not behave like a single long web document (D11).

**Page-level navigation.** Major resources change the current view rather than appending another
section below the previous one:

```
HQ
├── Dashboard
├── Clients
├── Organizations
├── People
├── Roles
├── Modules
├── Operations
├── Audit
└── Settings
```

Clients → People is a **view transition**, not a longer page.

**Contained scrolling** (D13) for: data tables · long lists · activity feeds · logs ·
notifications · command results · dense dashboard regions · long navigation lists.

Avoid unnecessary body scrolling when the shell can remain fixed. **But do not blindly force every
page into a fixed-height scroll container either** — scroll ownership is determined per page and
recorded.

### 5.7 — Sidebar behaviour

```
┌──────────────────┐
│ VERITY           │  ← stable, never scrolls
│ workspace        │
├──────────────────┤
│ navigation       │
│ navigation       │
│ navigation       │  ← this region alone scrolls,
│ navigation       │    and only when required
│                  │
├──────────────────┤
│ settings         │  ← stable where appropriate
│ profile          │
└──────────────────┘
```

Requirements: no scrollbar when navigation fits · scrollbar only when required · header stable ·
bottom utility area stable · navigation region alone scrolls · behaviour correct at differing
viewport heights · permission-filtered navigation still correct · a long client/module list must
not break the shell.

**Explicit test matrix:** 1440px desktop · 1024px desktop/tablet · 390px mobile · short viewport
height · large navigation set · small navigation set.

### 5.8 — Scope

**Brand:** logo · mark · clearspace · favicon / app icon · typography identity · brand usage.

**Product UI:** light theme · dark theme · neutral surfaces · gradients · glass system ·
configurable accent · semantic colours · type scale · spacing · radius · shadows · borders ·
controls · tables · forms · charts · navigation · empty states · error states · loading states ·
confirmation states.

### 5.9 — Contrast is re-verified, never assumed

ADR-011 constraint 1 binds: **the value changes, never the requirement.** `#00D1B2` as text on
white measures ≈1.9:1 and fails AA badly, which is exactly why the computed fill/ink ladder exists
and must be retained. Each adjusted value is recorded in ADR-012 — as `--color-text-tertiary`
already was when the board's `#7A7A7F` failed at 3.9:1.

## 6. Phase 2 — Global HQ and Administration

**Goal:** HQ becomes an actual operational console. The Verity team manages clients **without
coding or SQL** (D16, D20). This is the largest change from Revision 2, which deferred it.

### 6.1 — What HQ is today

`implementation/` records **EXPERIENCE SHELL: READY**. That verdict is about visual fidelity,
brand, accessibility and contribution-driven architecture, and on those axes it holds. **It is not
a claim about operability** and must not be read as one (D6-adjacent: two claims, reported
separately).

**Architecturally sound.** Navigation is genuinely contribution-driven — the shell holds no
capability-to-route map; `navigationFor()` filters by resolved permissions, so a role that cannot
read an entity never sees its nav item. Organization switching re-verifies membership server-side.
Every mutation goes through `runCommand`, with the actor resolved from the session, never from a
payload. Errors carry a `retryable` flag rather than leaking a digest.

**Largely read-only.** Of twelve routes, the mutations reachable through the UI are: create a
Location, act on an Asset, decide an Approval, edit custom fields, switch organization, sign in and
out, change appearance. Everything else is a table.

| Gap | Consequence |
|---|---|
| No user / membership management | Cannot invite, assign a role, or revoke. `provisionIdentity()` is built and tested; nothing calls it outside the seed. |
| No role / permission management | Roles, compositions and field permissions exist in schema and resolver; no screen. Changing access means SQL. |
| No organization management | The hierarchy scoping depends on can only be seeded. |
| No tenant / client management | Required by D15–D16; does not exist at all. |
| No create path for Asset / Evidence / Booking | Four of five capabilities viewable but not populatable. |
| Global search | Decorative; blocked on a search API. |
| Notification bell → `/audit` | Honest, not a notification centre. |
| File upload cannot complete | Two-phase contract built and tested; no storage driver bound. |
| Nothing scheduled | SLA sweeps and notification dispatch implemented and idempotent; nothing invokes them. |

**Stated plainly:** a correct, well-built **read surface** over a proven foundation — not yet an
operable administration console. Closing that is Phase 2.

### 6.2 — The security problem, stated honestly

D15–D18 place HQ **above** client organizations. That is the `Global` permission scope, which
`CLAUDE.md` lists as an open decision: PLA-AUT-002 defines it, but `verity.resolve_permissions`
**deliberately filters `Global` grants out** so such a row cannot silently take effect — because
honouring it means bypassing the RLS that enforces INV-001.

Revision 2 deferred this. **Revision 3 puts it on the critical path** (D15, D19). It is a security
architecture decision, not a UI task, and it is resolved by ADR-013 **before** any cross-tenant
code is written.

### 6.3 — ADR-013 — Global HQ operator security model

**Mandatory. Blocks all of §6.5 onward.** The ADR must answer, each explicitly:

1. How does a Verity HQ operator authenticate?
2. How is HQ operator authority represented?
3. How does a global operator intentionally select a tenant?
4. How does the selected tenant context become authoritative?
5. How does RLS remain effective?
6. How are cross-tenant reads performed?
7. How are cross-tenant mutations performed?
8. How are these actions audited?
9. How does the system fail closed?
10. How is accidental tenant leakage prevented?
11. How are global operators separated from ordinary tenant users?
12. How are privileged actions distinguished in audit logs?

### 6.5 — Authentication and demo removal (D21, D22)

**There is no authentication bypass to remove.** What exists is a development fixture in

three Demo organizations, three roles, and Demo locations, assets, resources, bookings and

1. **Remove demo credentials from source.** Rewrite `seed.ts` to contain no credential and create
   no Demo records.
2. **Remove the demo auth identity.** Archive the demo platform identity rather than hard-deleting
   it — `CLAUDE.md` ends the identity lifecycle at `Archived` and there is deliberately no
   deprovision path — and remove the Supabase auth row so the account cannot authenticate.
3. **Bootstrap the real local HQ administrator.** New `prisma/bootstrap-admin.ts` reading
   `ADMIN_EMAIL` and `ADMIN_PASSWORD` **from the environment, never from source**. Carries forward

4. **Remote guard, mandatory.** The script refuses a non-local `DATABASE_URL` unless

   email's local part: acceptable for local development (D21), and **not** to reach a deployed
   environment by default (D22). The guard makes that a mechanism, not a convention.
5. **Verify real authentication.** Confirm sign-in goes through actual Supabase password
   verification, and that authorization comes from the real permission system rather than a

### 8.4 — Provider bindings

The principle stands: **a provider decision is driven by an actual client requirement, not guessed

| Job runner | SLA sweeps, notification dispatch, anything scheduled | The chosen client has a deadline |
| Notification transport | Reminders, alerts, "ready" messages | The chosen client notifies a person |

requirements determine which providers are bound, in what order.

## 15. Questions for Product Owner

Only genuinely unresolved items. Questions already answered by D1–D26 are not asked — Global HQ is
required, dark mode is required, glass remains, Steep's colours are not copied, client work cannot

### Blocking — the answer changes architecture or security

**QB-1 — Default accent: `#00D1B2` or `#D4A017`?**
`design/verity asthetics.png` is titled *VERITY BRAND IDENTITY* and labels `#00D1B2` **Primary** in
its UI style guide; both theme boards render in it. But `CLAUDE.md` states gold `#D4A017` is the
default "because that is the brand's colour", calls the mint boards "a preset, not a rebrand", and
lists **"do not replace gold with teal"** as an explicit anti-regression rule. Shipping `#00D1B2`
directly violates a written rule, so it is not done silently.
**Recommendation:** adopt `#00D1B2` as the default preset, keep the full preset system and custom
hex, keep the mark monochrome and never accent-recoloured (D9), and update `CLAUDE.md` plus ADR-012
in the same change so the repository's instructions and its code agree. Confirm.

**QB-2 — Does `#00D1B2` as accent collide with semantic success green?**
The boards show teal accent and green "In stock" status in the same table. Current semantic success
is `#3f7d53` / `#6fbe86`. With a teal accent, accent-tinted UI and success status risk reading as
the same signal — the one thing D4's "semantic independent of accent" is meant to prevent.
**Recommendation:** retune semantic success away from teal (cooler-neutral green, or a distinctly
different value) and prove separation by test. Confirm the approach, or state that the boards'
closeness is intended.

**QB-3 — Which cross-tenant mechanism does ADR-013 evaluate first, and who signs it off?**
D19 requires the ADR; D17 requires it be explicit, audited and fail-closed. The candidates —
audited operator path, controlled `SECURITY DEFINER`, explicit scope elevation — differ materially
in blast radius if wrong. **Question:** does the product owner want to review the option comparison
before a model is selected, or approve the ADR once written? This determines whether Phase 2.1 has
one review checkpoint or two.

**QB-4 — Where do HQ operator identities live?**
D18 requires tenant-scoped and global administration to stay distinguishable. Two shapes are
possible: a dedicated Verity operator tenant whose members hold global authority, or an operator
flag orthogonal to tenancy. This is an identity-model decision that ADR-013 depends on, and it
touches INV-003 (one Party per person). **Recommendation:** decide inside ADR-013 with both shapes
compared; confirm that is acceptable rather than pre-deciding here.

**Recommendation:** treat composition as the template for capability pages, discard the domain
